# Windows 高分辨率虚拟屏截图

Index 可以临时启用已安装的 MTT Virtual Display Driver，以 3840×2160@60 Hz 创建扩展桌面，
通过 Windows Graphics Capture 截取完整虚拟屏，或让当前窗口临时在该屏上保持逻辑大小、以更高
像素密度重新渲染后截取窗口。普通截图流程不依赖该驱动。

## 运行边界

- 驱动安装是可选操作。Index 启动、更新和普通截图不会安装、更新、启用或卸载驱动。
- 当前实现只识别监视器硬件代码 `MTT1337` 或明确名称 `VDD by MTT`，不会操作 Parsec、
  ToDesk、Oray 或其他虚拟显示器。
- 截图前保存当前活动 DisplayConfig 路径，只把 MTT 目标加入现有路径；不使用会重新选择所有屏幕的
  `SDC_TOPOLOGY_EXTEND`。
- 截图完成、取消或失败后恢复原路径。截图期间存在本地 ownership marker；若进程异常退出，下一次
  虚拟屏截图会先删除由 Index 遗留的 MTT 路径。
- 如果 MTT 是系统唯一的活动显示路径，自动恢复会拒绝把它移除，避免让 Windows 进入无活动屏幕状态。

## 使用

1. 通过上游提供的签名安装器或 Virtual Driver Control 安装驱动；安装和卸载需要用户显式操作并授予
   管理员权限。固定的上游源码位于 `third_party/virtual-display-driver`，它不会进入常规 .NET 构建。
2. 打开 Index 的快捷键设置页。
3. 若要截取空白虚拟桌面及其内容，在“高分辨率虚拟屏截图”中点击“截取完整虚拟屏”。
4. 若要让应用保持现有布局并以 4K 高 DPI 重新渲染，先激活目标窗口，再按“4K 当前窗口”快捷键；默认是
   `Ctrl+Shift+4`。
5. Index 会锁定当时的前台 HWND，临时启用 4K 虚拟屏、移动并调整目标窗口、通过 WGC 截取窗口，
   然后先恢复窗口位置和状态，再恢复原显示布局。

若不想每次点击“4K”，可在“设置 → 高分辨率虚拟屏截图”开启“自动 4K 窗口截图”：

- 普通框选后点击“完成”或“复制”，只要选区能关联到单个顶层窗口，就自动执行高 DPI WGC、使用
  第一次选区裁剪并完成原动作。
- 窗口预览后单击确认，或滚轮/Tab 明确选中的窗口，会锁定到其顶层 HWND；确认时不会重新猜测。
  只要拖拽形成自由选区，就丢弃按下点的临时窗口并使用最终选区中心解析目标。
- Index 可以截取自己的主窗口；覆盖层会在 4K 搬移开始前关闭，WinUI 线程继续处理 DPI 与布局消息。
- 无法关联 HWND 的任意桌面区域、钉图等动作仍使用普通冻结帧。
- 自动 4K 因驱动、窗口或显示拓扑失败时，会回退到本次普通冻结截图；手动点击“4K”仍保留明确的
  失败语义并重新打开原选区。

也可以从普通框选截图进入：

1. 启动普通截图，在目标应用窗口内完成第一次框选。
2. 窗口预览已选中可捕获窗口，或自由选区中心属于一个可捕获的顶层窗口时，工具栏中的“4K”按钮会启用。
3. 点击“4K”后，Index 释放旧冻结画面，按照“虚拟屏 DPI ÷ 原屏 DPI”放大窗口的物理像素边界，
   通过 WGC 捕获，然后恢复窗口和显示布局。例如 100% 缩放下的 1200×800 窗口会在 200% 的
   虚拟屏上渲染为 2400×1600，但应用看到的逻辑大小仍是 1200×800。
4. Index 将第一次选区与目标窗口的交集直接映射到高密度帧，按原始像素裁剪并保存，不再显示第二次
   框选。第一次框选已有的标注会按相同 DPI 比例映射。只有原来铺满 1920×1080 屏幕的窗口才会产生
   完整 3840×2160 窗口帧。

任意桌面区域无法凭空得到额外细节，因此“4K”只对能关联到单个顶层 HWND 的选区启用。第一次选区
超出窗口的部分不属于该 HWND，最终只保存它与窗口相交的区域。

Index 在第一次异步屏幕捕获前同步冻结窗口 HWND、PID、Z 序和边界。执行 4K 搬移前会再次核对 PID
与边界；窗口已经移动、缩放、关闭或 HWND 被复用时，本次高分辨率捕获会中止，不会改为截取另一个窗口。

驱动必须公开 3840×2160@60 Hz 模式。若模式缺失，Index 会返回可诊断错误，不会改用较低分辨率冒充
4K。“4K 当前窗口”会校验 WGC PNG 的 IHDR 必须等于按两个显示器 DPI 比例计算出的暂存窗口尺寸；
不会把普通低分辨率窗口插值放大冒充高密度渲染。16:10 等窗口按 2 倍密度后可能略高于 16:9 的
3840×2160 虚拟屏；Index 会保持完整窗口合成表面供 WGC 捕获，不会为塞进显示器而缩小并改变布局。
虚拟屏缩放不高于原屏、目标窗口限制最大尺寸或拒绝跨屏移动时，该次截图会失败并恢复原位置。当前
机器的 MTT 显示器应设为 200% 缩放；更高的 5K/8K 模式需要先由驱动配置公开，当前 UI 尚未提供。

## 验证记录

2026-08-28 在 Windows 11 x64 上完成过真实验证：MTT 从 inactive 临时启用，切换至
3840×2160@60 Hz，WGC 输出 PNG 的 IHDR 为 3840×2160，随后 MTT 回到 inactive，ownership
marker 被清除。该记录不代表 Release UI 已查看或发布包已启动。

2026-09-01 的早期“4K 当前窗口”链路验证曾将另一个正在运行的 Index
窗口从 1086×713 暂存为 3840×2160，WGC 输出 2,887,193 字节 PNG，IHDR 为
3840×2160；图像目视确认为重新排版后的 Index 窗口内容，不是黑帧或空虚拟桌面。截图后目标进程
继续响应且 HWND 未变化。此次验证直接调用生产 frame source；由于 Computer Use native pipe 不可用，
未自动注入全局快捷键。该强制铺满方案现已被 DPI 保真方案取代，不代表当前尺寸语义；新链路的真实
验证结果应另行记录。

2026-09-01 对 DPI 保真链路再次执行真实验证：MTT 虚拟屏报告 200% 缩放，另一个 Index 窗口的
原始可见边界为 1086×713，暂存后 WGC PNG 的 IHDR 为 2172×1426，宽高均严格为 2 倍；截图后
目标进程继续响应并恢复原 HWND。该验证覆盖生产 frame source、窗口恢复和 WGC 尺寸校验；工具栏
“首次框选 → 直接保存”的交互映射由单元测试覆盖，尚未通过桌面自动化注入真实点击。

同日针对 1920×1200 屏幕上的 Warp 最大化窗口复现并修复边界问题：窗口可见边界为
1920×1152，2 倍暂存表面为 3840×2304，虽然高度超过 4K 虚拟屏 144 像素，WGC 仍完整输出
3840×2304 PNG；窗口随后恢复且进程继续响应。

自动模式回归中还发现：若在启用 MTT 后才读取源窗口 DPI，Windows 可能先按记忆的虚拟屏位置自动
迁移窗口，使暂存器误以为源窗口已经是 200%，并把真实 2× WGC 帧当成尺寸错误回退。当前实现会在
任何显示拓扑变化之前锁定 HWND、WINDOWPLACEMENT、原始边界、源屏边界与 DPI。资源管理器真实
验证由 196×236 得到 392×472，宽高严格为 2 倍；窗口恢复且进程继续响应。

同日 17:43 对 Release UI 执行了 Index 自截真实回归：通过全局 `Ctrl+1` 进入普通框选并确认自动
4K，冻结目标始终为当前进程的同一个 HWND。原始可见边界 1086×713，WGC PNG IHDR 为
2172×1426，保存的 shot 61 目视确认为 Index 图库界面而非后方资源管理器；完成后 HWND 未变化，
原始 raw bounds `156,156,1256,876` 完整恢复且进程继续响应。WinUI 的异步 DPI 重排需要连续三次
稳定边界观测后才开始 WGC，否则可能在首次到达目标尺寸后再次调整窗口。

2026-09-02 修复自由选区错误继承按下点窗口的问题。真实回归从 Index 窗口内拖出
`519×300` 选区，日志锁定同一 Index HWND/PID，WGC 窗口帧为 `2172×1426`，最终裁剪为
`1038×600`；shot 65 目视确认为选区对应的 Index 图库内容。此前 shot 62 的保存 metadata 按最终
选区识别为 Index，但 WGC HWND 为后方资源管理器，证明错误发生在选区目标绑定而非持久化阶段。

同次回归还发现：同进程 WinUI 窗口从 200% 虚拟屏恢复到 100% 物理屏后，可能延迟把尺寸缩为一半。
恢复流程现与暂存流程一样，必须连续三次观测到原始可见边界才允许完成。shot 68 与随后一次 shot 69
连续命中同一个 Index HWND；shot 68 的自由选区为 `552×302`、输出 `1104×604`，截图前后 raw bounds
均为 `208,208,1308,928`，PID/HWND 未变化且进程继续响应。两张 PNG 均目视确认为 Index 内容。
